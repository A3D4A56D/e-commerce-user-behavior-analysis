# 电商用户行为数据分析（Taobao UserBehavior）

基于淘宝用户行为公开数据集的端到端分析项目：本地 CSV → Python 批量入云 → SQL 分层分析 → 业务指标结论。

## 一、项目背景

电商平台每天产生大量用户行为日志（浏览、加购、收藏、购买）。本项目的目标是把这份原始日志变成可读的业务指标：用户都做了什么、哪天的流量最高、从浏览到购买漏在哪一层。

## 二、数据

| 项 | 内容 |
|---|---|
| 来源 | 阿里云天池 · User Behavior Data from Taobao |
| 规模 | 500,000 条行为记录 |
| 用户数 | 4,845（有浏览行为的独立用户） |
| 时间范围 | 2017-11-24 至 2017-12-03（另有少量早于 11-24 的异常记录，见"已知局限"） |
| 字段 | `user_id`、`item_id`、`category_id`、`behavior_type`（pv / cart / fav / buy）、`timestamp`（Unix 秒） |

> 说明：原始文件约 1 亿条，受免费云数据库 1GB 存储限制，本项目取文件前 50 万条。

## 三、技术栈

- **Python 3** + `PyMySQL`：读取 CSV、分批（2 万行/批）批量写入云端数据库，避免单次事务过大
- **Aiven MySQL 8.4**（云数据库，强制 SSL）：数据存储与查询
- **DBeaver**：SQL 开发与结果校验
- **SQL**：聚合、`CASE WHEN`、窗口函数 `ROW_NUMBER`

## 四、做了什么

1. **数据接入**：`import_data.py` 连接云端 MySQL（SSL 证书校验），按批读入并提交，50 万行导入耗时 56 秒；密码通过环境变量/运行时输入，不写入代码。
2. **建表**：`user_behavior` 表，`id` 自增主键（Aiven 要求 `sql_require_primary_key`），`timestamp` 存 BIGINT 原始秒级时间戳。
3. **数据探查**：总量校验（50 万行）、按天分布、行为类型分布。
4. **指标计算**：PV / UV、按天 PV 趋势、用户-日转化漏斗、每个用户最后一次行为（窗口函数）。

## 五、主要结论

**行为类型分布**（四类合计 500,000 条，与表总行数一致，校验通过）

| 行为 | 次数 | 占比 | 用户数 |
|---|---|---|---|
| pv 浏览 | 449,357 | 89.87% | 4,845 |
| cart 加购 | 27,509 | 5.50% | 3,664 |
| fav 收藏 | 12,950 | 2.59% | 1,871 |
| buy 购买 | 10,184 | 2.04% | 3,376 |

- 购买行为只占全部行为的 2.04%，平均 **44 次浏览才对应 1 次购买**。行为日志的主体是浏览，转化信号极其稀疏——这也是电商必须做漏斗分析的原因：只看总量会高估用户的购买意愿。
- 各类型"次数/用户数"差异明显：浏览约 92.7 次/人，加购约 7.5 次/人，购买约 3.0 次/人，符合"越靠近成交越低频"的常识。

**转化漏斗（用户-日口径）**

| 环节 | 用户日数 | 相对浏览 |
|---|---|---|
| 有浏览（pv） | 34,205 | 100% |
| 有加购（cart） | 11,750 | 34.35% |
| 有购买（buy） | 6,735 | 19.69% |

- 浏览到加购丢掉了三分之二的用户日，是漏斗上最陡的一层。
- 加购到购买相对平缓（19.69% / 34.35% ≈ 57%），说明"已加购的人下单意愿更强"，运营的重点应放在**促加购**而不是催下单。

**时间特征**：流量高度集中，2017-11-25 单日 52,042 条，远超其余日期，存在明显的大促式脉冲。

## 六、已知局限

写在前面：这些偏差我知道，也正因为知道才没往大了写。

1. **样本非随机**：取的是文件前 50 万条，对应约 4,845 个用户的完整行为序列，属于高频用户，转化指标会系统性偏高。
2. **用户-日口径 ≠ 会话漏斗**：同一自然日内的浏览、加购、购买只按"是否发生"统计，不要求时间先后，因此 19.69% 高于行业 session 级 2%–5% 的常规水平。
3. **时间窗口短**：数据只覆盖 10 天，无法做周同比、月趋势。
4. **存在脏数据**：少量记录的时间戳早于数据起始日（2017-09-11 等），原因未查明，未做清洗，仅在此标注。
